# opener 排序策略

> **状态**：⏸️ 挂起（问题已确认、候选方案已收集，具体选型未定；解挂条件见文末）

## 背景：最近使用排序对「组合型」用户是反向信号

现状：项目打开时按 opener 的**最近使用**排序只存在于 alfred 出口——`opener-search` 用 `UsageService().LatestOpeners(path, 3)`（按 opener 去重、取最新一次使用时间倒序）把最近用过的排前面，其余按 settings.json 手动序垫底（`cmd/alfred/opener_search.go` 的 `sortOpeners`）。Web 项目页的 opener 快捷入口目前是纯手动序，未接 usage。

问题：最近使用排序隐含的假设是「你会重复用同一个 opener」。但实际使用模式是「每个项目有一组固定的工作台组合」（如 ZCode → 浏览器 → 终端），每次按同样顺序开一遍。最近使用排序会让这个集合**每开一轮就轮转一次**——上次最后开的排到第一，下次想先开的那个反而被挤下去。对固定组合场景，最近使用是反向信号。

usage 数据基础已具备：1034 后打开记录为 `state/usage.jsonl`（逐条含时间戳），任何按时间/次数聚合的策略都有数据可算。

## 候选方案

### 单信号

| 方案 | 说明 | 优 / 劣 |
|---|---|---|
| 最近使用（MRU，现状） | 按最新一次使用时间倒序 | 适合重复单点；组合场景轮转乱序 |
| 频次（MFU） | 按累计次数 | 长期稳定；状态迁移慢，旧习惯计数压着新习惯 |
| 首次使用序 | 按该项目上第一次使用的时间 | 天然贴合「组合按固定顺序开」的心智；语义隐晦，产品界少见 |

### 组合算法（主流方向）

| 方案 | 说明 | 优 / 劣 |
|---|---|---|
| MRU + 频次混合 | 频次为主、同频按最近 | 朴素组合，很多启动器的默认 |
| LFU with aging | 频次随时间指数衰减（半衰期参数） | 稳定 + 能淘汰旧习惯；衰减周期需调参 |
| 滑动窗口频次 | 只统计最近 N 天/N 次内次数（`count where opened_at > now-7d`） | aging 的离散简化，一条查询即实现 |
| 衰减 MRU | score = 最近使用的新鲜度 `2^(-Δt/半衰期)` | 修「一个月前用过一次一直压前面」；本质仍是 recency |
| Frecency（Firefox 地址栏） | 按新鲜度分桶赋权（如 8 天内 ×8、更早 ×4/×2/×1），score = 加权和 | 衰减频次的工程化变体，一条 SQL 分桶求和；经 Firefox 长期验证 |

### 带结构

| 方案 | 说明 | 优 / 劣 |
|---|---|---|
| 序列模式 / n-gram 条件预测 | 记 `(project, prev_opener, opener)` 次数，按上一次 opener 条件化排序——开了 A 之后通常开 B，则 B 排第一 | 唯一能表达「组合内顺序」的方案，最贴合场景；冷启动空、结构复杂、单用户数据稀疏需斟酌 |
| 会话聚合（burst grouping） | N 分钟内连续 open 归为一个「组合事件」：组合按频次排、组内按首次序排 | 自动「学会」工作台组合，n-gram 的轻量版；时间窗口参数难解释 |
| 显式优先级分层 | 手动 pin/拖拽序恒在最上，自动排序只作用于未 pin 部分 | 可预测性兜底，适合作为任何自动策略的安全垫 |

## 初步倾向（待讨论确认）

按性价比排序：

1. **一步之遥**：滑动窗口频次（7 天窗口）——一条查询，稳定性立刻解决；
2. **最推荐**：Frecency（分桶权重）——比窗口频次更平滑，同样一条查询；
3. **最贴合组合心智**：n-gram 条件排序——能表达「开了 A 之后通常开 B」，但要评估单用户数据量是否够学出来。

无论选哪个，建议保留：

- 「有过使用的一组在前、从未使用的按手动序垫底」的两段结构（`sortOpeners` 现有行为）；
- 显式优先级分层（方案 11）作为安全垫：settings.json 手动序是事实源，自动只排未固定部分。

实施落点预估（若选定）：`usage` 包加聚合查询函数（如 `TopOpeners` / frecency 打分），alfred 侧换调用；Web 项目页是否接同一策略可一并讨论（当前是纯手动序）。

## 为什么挂起

- 排序信号选型（频次 / frecency / n-gram / 分层组合）需要结合实际 usage 数据量和体感再定，不适合拍脑袋直接实施；
- 非痛点阻塞项，属于「有更好、没有不痛」的体验优化。
