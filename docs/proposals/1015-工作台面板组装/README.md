# 工作台面板组装：自定义布局 + 面板注册收口

> **状态**：📋 待办（方向已定，细节待 1011-1014 落地后按实际体验设计）
>
> **所属**：[`1008-workspace工作台` 总纲](../1008-workspace工作台/README.md)（先读总纲「已收敛的全局决策」）。
> **依赖**：1011（git 树）、1012（代码阅读）、1013（diff）、1014（PTY）全部完成。**必须最后做**。

## 背景与目标

工作台的长期形态：**同一页面自定义布局**，同屏组合 git 信息、代码、diff、命令行 PTY（例：左 git 树 + 右上代码 + 右下 diff + 底部终端）。1010-1014 期间所有面板跑在基座的固定布局里（左 git 树 + 右内容 + 底部 PTY 抽屉），且从第一天遵守「面板自带数据 hook、只通过 URL 通信」的铁律——本提案把这条铁律兑现成可组装的布局系统。

**本提案不做**：新增任何面板能力、多项目同屏、布局分享导出。

## 方案方向（细节届时定）

### 1. 布局模型

- 采用**分区网格/分栏树**模型：页面是递归的分割结构（横向/纵向分割，叶子是面板槽位），类似 VSCode 面板/dock 布局的简化版。不建议引入完整 react-grid-layout 类拖拽库（带自带样式与复杂度），倾向基于分割树 + 简单拖放（HTML5 drag 或 pointer 事件手写），选型时评估 `react-resizable-panels`（无主见样式、可组合分栏，与 Tailwind/shadcn 兼容好）作为分割容器，拖拽换位手写。
- 布局持久化：结构化 JSON 存 localStorage（key 含 `cube.workbench.layout`），后续可升级到后端 config 节（`config.json` 加 `workbench` 节即完成，符合「命令式改 config」现状）。不进 URL（URL 管选中态，布局是个人偏好）。

### 2. 面板注册表

- 建 `web/src/pages/workbench/registry.ts`：面板注册表（id、名称、图标、组件、可接受的源类型约束——如 diff 面板要求双源、代码面板单源）。
- 固定布局改为「默认布局 JSON」；同类型面板可开多实例（如两个代码面板对比不同源）时，URL 参数需带面板实例维度（如 `&p1.file=...`）——**这是本提案最大的设计难点**，届时重点设计；MVP 也可先限制同类型面板单实例规避。

### 3. URL 状态总线收口

- 1011 的 `params.ts` 升级为全局状态协调器：布局中每个面板槽位声明它消费/产出的 URL 参数命名空间，避免多实例冲突。
- 保持总纲承诺：分享/刷新恢复优先恢复「选中态 + 面板类型」，布局本身按接收者本地配置。

## 验收标准（届时细化）

1. 可在页面内添加/移除/移动面板，组合出「git + 代码 + 终端」同屏布局。
2. 布局刷新后保持；URL 分享在对方机器上打开后选中态正确呈现（布局用对方本地的）。
3. 所有既有面板在自定义布局下功能不退化（各面板测试口径回归）。
4. `pnpm -C web build` 通过；前端为本提案主要工作量，后端预计无改动。

## 实施注意

- 本提案几乎纯前端；开始前重读 1010-1014 各面板对 URL 参数与 hook 的约定，收口时不得破坏。
- 拖拽交互注意 Base UI 组件的事件兼容（不用 Radix 生态的 dnd 库写法）。
