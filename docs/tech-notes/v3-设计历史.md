# v3 设计历史笔记

> 本文从已删除的 `docs/design/v3-design.md` 提炼有价值的**设计决策推理与历史**。
> 现状描述见 [`../spec/现状.md`](../spec/现状.md)；本文只记录「为什么这么设计」的历史。

---

## 一、v2 → v3 的演进动机

v3 相对 v2 的核心变化是**按领域重构**。v2 的代码组织偏过程式，v3 引入了明确的分层架构（基础设施/能力/领域/出口/装配）和依赖纪律。

## 二、Workspace 实体的取舍

**v2 曾有 `Workspace` 一等实体**（独立的 service + 数据结构）。v3 简化为 `ScanRule` + `group` 字符串字段。

理由：`group` 保留了 workspace 的全部实用价值（分组聚合、批量作用域），但不再需要独立实体和 service。一个 ScanRule 扫一个根目录，命中的项目归属该 `group`——`group` 承担「物理目录约定 + 分组聚合 + 批量作用域」三重价值。

## 三、多 domain 平台定位的淡化

v3 设计初期定位是「本地开发工具集合平台」，设想 project 是首个 domain，未来平级加入 sqlite 管理（`cube db`）、端口查看等。`docs/design/v3-design.md` 第六节的 CLI 示例就含 `# 未来: cube db list / query`。

后续实践中这个定位有所淡化——cube 更聚焦于「项目管理」本身，新 domain 的扩展不再作为近期目标。但分层架构和扩展模型（五处加法）保留了扩展能力，只是不主动推进。

## 四、里程碑历史

| 里程碑 | 状态 | 内容 |
|--------|------|------|
| 第 0 步 | ✅ | 包结构重组、去 wire、HTTP 表层合并 |

## 五、待细化的设计点（未决）

以下问题在 v3 设计阶段提出，至今未完全收敛：

- M2 批量操作并发/失败策略（全失败回滚 vs 部分成功 vs best-effort 报告）。参考 [`../references/gitbatch.md`](../references/gitbatch.md) 的避坑点。
- worktree 物理位置约定（固定目录 vs 项目 `.git/worktrees/`）。
- diff API 返回结构（patch 文本 vs 结构化 hunks）。
