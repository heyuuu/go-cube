# 模板引擎设计（讨论详情）

> 本文记录设计讨论的全过程上下文：背景、推导、排除的方案、最终结论的理由。
> 给 AI 理解「为什么这么定」用。结论本身见 `README.md`。

---

## 一、起点：需求

用户想做一个**模板工程**，用于快速初始化新项目。模板可能包括前端、后端、基础配置、初始接口、脚本、demo 页等，创建时需要替换名称等内容。

---

## 二、约束澄清（通过多轮提问确认）

### 2.1 用户的明确选择

| 决策点 | 用户选择 | 含义 |
|---|---|---|
| 技术栈 | 前后端分离，不用 monorepo；根目录 Go 后端 + `frontend/` 是 Vite+React | 后改为：**引擎必须技术栈无关，不绑死任何选型** |
| 生成方式 | CLI 脚手架（自写），`go install` 全局安装 | Go 实现，不是 Node |
| 包含内容 | 前端工程 + 后端工程 + 基础配置 + 脚本文档 | 全都要，但这是模板内容，不是引擎职责 |
| 模板组织 | 多套模板共存（web / cli / service 等） | 引擎是通用调度器，模板是数据 |
| 变量来源 | 参数 + 交互都支持 | 有参数走参数，缺的交互问 |
| 条件裁剪 | **不做**，用多模板代替 | 不搞 `when` 条件，差异靠维护不同模板 |
| 后置动作 | 模板声明动作，引擎执行 | 引擎不写死初始化逻辑 |

### 2.2 用户后来的重要修正

> 「你不要去管模板的具体内容，模板的具体内容甚至技术栈是随时可以改的。现在的关键问题是模板的通用能力应该怎么去实现？」

这是关键转向：**把重心从「某一套技术栈的模板内容」移到「引擎的通用机制」**。引擎对技术栈一无所知。

### 2.3 用户对存放位置的明确

> 「模板不是这个 cove 的事情……这个会话只是讨论模板引擎功能……」
> 「go install 安装到全局，直接 cli 使用。」
> 「之后再考虑（模板内置还是外拉），可能会有合并到其他工具（比如 cube）的考量。」

→ 引擎和 Cove 体系解耦，是独立工具。

## 三、合进 cube 的决策

### 3.1 cube 是什么

- `github.com/heyuuu/cube`，本地优先的项目管理工具，Go 写的
- 核心能力是扫描本地文件系统的 `.git` 目录，管理本地项目
- 成熟的 v3 项目，已按领域重构，有完整分层架构
- 定位硬：不绑 AI、不绑 Cove、独立演进（Cove 决策 D-29 将 Cube 移出 Cove 体系）

### 3.2 为什么合进 cube 而不是单独工具

**理由 1：职责天然衔接——从「管理项目」到「创建项目」**

cube 已经在做「扫描和管理已有项目」。创建新项目是它的**前序动作**。管理一个项目的生命周期，起点就是创建它。`cube scan`（发现项目）和 `cube create`（生成项目）是同一领域内的两个动作。

**理由 2：技术栈零摩擦**

模板引擎用 Go 写，cube 也是 Go。`go install` 全局 CLI 的分发方式完全一致。没有跨语言、跨进程、跨部署的问题。

**理由 3：避免工具碎片化**

单独建一个 scaffold 工具，意味着多一个要 `go install`、要记命令、要维护 release 的东西。cube 作为「本地项目工具箱」，吸收创建能力后职责更完整。

### 3.3 前提：引擎保持内聚

合进 cube 不等于把模板逻辑和项目管理逻辑搅在一起。应该做成 cube 里的一个**独立子系统**（如 `internal/scaffold/`），对外只暴露 `cube create`，内部不依赖 cube 的 project 管理包。这样哪天想拆出来复用，零成本。

### 3.4 用户最终确认

> 「因为已经引入了 Cube，结论就是 Cube 加一个 create 命令。新建一个模板库。
> 因为命令和模板分开了，所以只能使用协议来约束。所以我希望这个协议尽量简单明了。」

→ 定案：**cube 加 `create` 命令，模板独立，靠协议约束。**

## 四、占位符语法的讨论（关键转折）

### 4.1 用户提出的问题

> 「业内通用的模板变量还有啥写法？不太喜欢 go template 的 `{{.var}}` 语法，凭直觉总觉得多个 `.`」

### 4.2 列举的业内方案

| 语法 | 示例 | 干净度 | 冲突风险 | 采用方 |
|---|---|---|---|---|
| Go template | `{{.project_name}}` | ❌ 有 `.` | 中 | Go 生态 |
| Mustache | `{{project_name}}` | ✅ | 高（和 Go/C++/JSON 模板冲突） | 最广 |
| Jinja2 | `{{ project_name }}` | ✅ | 高 | Python/Helm/Terraform |
| Shell | `${project_name}` | ✅ | 高（JS/Bash） | Shell 生态 |
| 下划线 | `__project_name__` | △ 啰嗦 | **几乎为零** | 老牌/私有脚手架 |
| ERB | `<%= project_name %>` | ❌ | 中 | Ruby/Plop |

### 4.3 关键洞察：占位符不该由引擎定

用户提出了颠覆性思路：

> 「不要 cube create 来定用什么模板变量形式。由模板来自己定义，cube create 只做文本替换。
> 比如在模板根目录定义 template.yaml，里面定义 patterns: glob + pattern + replace」

这个设计的精妙之处：

1. **把「占位符」和「变量」彻底解耦**：模板文件里写什么占位符，完全由模板作者定。引擎不需要认识任何特定占位符。
2. **占位符语法的争论在引擎层面消失了**：因为引擎不关心模板文件里用什么记号，它只执行 `pattern → replace`。
3. **`${var}` 只在 template.yaml 内生效**：不泄漏到模板文件里，模板文件的占位符由 `pattern` 字段定义。
4. **glob 给替换规则加了「作用域」**：`**/*.go` 只替换 Go 文件，避免误伤。

→ 这成为协议的核心设计。

## 五、替换规则的细节讨论

### 5.1 精确字符串 vs 正则

确认：**精确字符串替换**。理由：
- 占位符就是要 100% 精确匹配
- 避免正则的 escape 地狱
- 将来需要正则再加可选字段 `regex: true`

### 5.2 路径 + 内容统一替换

用户确认：**glob 匹配到的文件，其路径（含文件名）和内容都应用相同的替换规则。**

这样目录名 `__PROJECT__/main.go` → `my-app/main.go` 自动处理，不用单独的 rename 机制。

### 5.3 数据结构：按 glob 分组

用户纠正了「语法糖」的措辞：

> 「加个语法糖（比如多条规则共享一个 glob），不算语法糖吧，就是改变了数据结构」

正确。这是数据结构选择，不是糖。两种结构对比：

**结构 A（扁平，每条自带 glob）：**
```yaml
patterns:
  - glob: "**/*.go"
    pattern: __MODULE__
    replace: github.com/${author}/${project-name}
  - glob: "**/*.go"
    pattern: __PROJECT__
    replace: ${project-name}
```

**结构 B（按 glob 分组）：**
```yaml
patterns:
  "**/*.go":
    - pattern: __MODULE__
      replace: github.com/${author}/${project-name}
    - pattern: __PROJECT__
      replace: ${project-name}
```

采用 **结构 B**，理由：现实中「同一类文件往往有多个占位符」，分组后 glob 只写一次，更贴合心智模型。功能上两者等价，纯粹是结构偏好。

## 六、glob 规则的讨论

### 6.1 用户的疑问

> 「glob 规则你列出来对比一下……听你意思有很多不同种写法」
> 「doublestar、minimatch 的规则有统一的规范文档么？RFC 之类的？」

### 6.2 结论：没有 RFC

glob 从来没有过正式标准。`**`（递归匹配）是各家后加的扩展，行为不一致。现状：
- POSIX 只定义基础 `*` `?` `[...]`，无 `**`
- bash / doublestar / minimatch 各自为政
- 没有任何 RFC 统一规定 `**` 应该怎么匹配

### 6.3 Go 标准库 filepath.Glob 的局限

用户问 `filepath.Glob` 的规则。查证结论：
- 支持 `*`（不跨 `/`）、`?`、`[abc]`、`[^abc]`、`[a-z]`
- **不支持 `**`**（递归匹配）
- **不支持 `{a,b}`**（花括号分组）
- 对模板引擎来说「递归匹配所有 .go 文件」这个核心能力做不到

→ 所以 Go 生态的工具都用 doublestar，不用标准库。

### 6.4 最终策略：以 doublestar 为准，兼容 minimatch

详见 `glob-rules.md`。核心：
- 协议定义一个 glob 子集，以 doublestar 语义为基准
- 列出与 minimatch 的不兼容点（dotfile 默认行为、取反语法）
- Go 实现用 doublestar 库兜底

## 七、排除的方案及理由

### 7.1 排除：Go template `{{.var}}`

- 那个 `.` 是 Go template 区分字段访问的设计，对纯替换场景是噪音
- 用户直觉排斥

### 7.2 排除：`{{mustache}}` / `${shell}` 作为引擎固定占位符

- 都有冲突风险（JSON/YAML/代码里可能合法出现）
- 更根本：**引擎不该认识任何固定占位符**，占位符由模板定义

### 7.3 排除：变量派生进协议（camelCase 自动生成）

- 派生规则是复杂约定，塞进协议会让协议变重
- 不同语言/场景需要的变体不同
- 先不做，痛点出现再加

### 7.4 排除：条件裁剪（`when` 字段、勾选「要不要 Docker」）

- 用户明确选择「用多模板代替」
- 引擎更简单，差异靠维护不同模板解决

### 7.5 排除：引擎内置固定初始化步骤

- 不写死 git init / 装依赖
- 所有初始化由模板的 init 声明，引擎只执行

### 7.6 排除：引用 filepath.Glob 作为 glob 标准

- 连 `**` 都不支持，不满足模板需求

### 7.7 排除：引用某个第三方库作为协议标准

- 协议绑死第三方库，库改了协议跟着漂移
- 选择自定义子集，协议自包含
